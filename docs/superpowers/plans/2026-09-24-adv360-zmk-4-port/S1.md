# S1 — C4 backlight (brightness scale, defaults, ext-power settings off, K2 backlight API) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The adv360 backlight behaves as on the Kinesis pin. It is scaled by `ZMK_BACKLIGHT_BRT_SCALE` (default 25 %), starts from `BRT_START` 100 by default, never persists ext-power state, and `&bl` runs on the central only. The right half gets the K2 apply API (`struct backlight_state`, `zmk_backlight_update_vals`) that S3's peripheral handler calls.

**Architecture:** This section ports the Kinesis hunks of `backlight.c`, `backlight.h`, `ext_power_generic.c`, `behavior_backlight.c` and `app/Kconfig` except the central-side sender. The sender (`zmk_split_bt_update_bl`, the `split_peripheral_status_changed` listener and the 2.5 s timer) belongs to S3, which re-hosts it on K1 under R2's rules. The adv360 values are pinned in S0's Kconfig check. Two new native_sim suites cover the scale (`brt-scale`) and the K2 API (`update-vals`). The API suite is a zephyr module that calls the API from `SYS_INIT`, because no keymap binding reaches it. A 5-line `run-test.sh` hook makes that possible.

**Tech Stack:** C (Zephyr 4.1, ZMK), Kconfig, ZMK native_sim test harness, the K6 Docker harness from S0.

## Review Focus

1. **Double scaling on the right half.** K1's `set_kinesis_backlight.brightness` comment says "already scaled". If S3 sends a scaled value, the right half scales it again (25 % of 25 %), so it glows at 1–6 % while the left is at 5–25 %. Expected: the wire carries the unscaled `state.brightness` (0–100, as the Kinesis pin sent `&state`), and each half applies its own `BRT_SCALE`. Pinned here by `update-vals`: `{60, on}` must log `15%`, not `60%` and not `3%` (S1-T2). Recorded as a contract correction for S3.
2. **Out-of-range brightness from the split link** (a corrupt or future-format BL payload, K3 byte 0 > 100). Expected: clamped to 100, like `zmk_backlight_set_brt`, never passed to `led_set_brightness` out of range. Pinned by `update-vals` `{250, on}` → `25%` (S1-T2).
3. **Scale lost or wrong at the low end.** `BRT_START=20` × 25 % = 5 % on the board. Integer division means 1–3 % user brightness shows as 0. Expected: exactly the Kinesis arithmetic `brt * SCALE / 100`: 100→25, 80→20, 60→15, 40→10, 20→5, 0→0. Pinned by `brt-scale` over the whole BL_DEC ladder, and by the Kconfig check asserting `BRT_START=20` / `BRT_SCALE=25` on both halves (S1-T1).
4. **Upstream default drift.** Upstream sets `BRT_START` 40 in `app/Kconfig.defaults`. Kinesis's `default 100` has to actually win, or every board that relies on the default silently starts at 40. Expected: an unset `BRT_START` resolves to 100. Pinned by `brt-scale`'s first line `25%` (100 × 25 %), which is `10%` if 40 wins (S1-T1).
5. **The six upstream backlight suites silently re-baselined.** Setting `ZMK_TESTS_AUTO_ACCEPT` would overwrite their snapshots with the scaled values. Expected: the six snapshots stay byte-identical to `main`, and only their `native_sim.conf` gains the Kinesis lines (`BRT_SCALE=100`, `BRT_START=40`). Checked by `git diff --stat -- 'app/tests/backlight/*/keycode_events.snapshot'` printing nothing (S1-T1 step 5).

## Scope notes (read from the Kinesis diff, verified in the prototype)

- **In S1:** Kconfig `ZMK_BACKLIGHT_BRT_SCALE` (K4 text verbatim, including Kinesis's copy-pasted prompt), the `BRT_START` default 100, the scaling line in `zmk_backlight_update`, `struct backlight_state` moved to the header, `zmk_backlight_update_vals`, the whole Kinesis `ext_power_generic.c` hunk (settings removed, `ext_power_save_state` returns 0), the `behavior_backlight.c` locality GLOBAL→CENTRAL, and the Kinesis test-conf lines retargeted to `native_sim.conf` (R4).
- **Not in S1 (S3 owns):** the `#include <zmk/split/bluetooth/central.h>` (deleted upstream, #2766), `zmk_backlight_central_send`/`bl_update_work`, the `split_peripheral_status_changed` subscription and the 2.5 s reschedule. R2 rule 3 replaces them with a re-send from `split_central_security_changed`. S3 adds its send call inside `zmk_backlight_update` in `app/src/backlight.c`, so `backlight.c` is a hot file: S1 before S3.
- **`BRT_START` default 100 goes in `app/Kconfig.defaults`** (replacing upstream's `default 40`), not as a second `default` in `app/Kconfig` the way the pin did. The effect is the same today: app/Kconfig's default was first in definition order, so it won on the pin, and `brt-scale` proves 100 wins here. This way board `Kconfig.defconfig` defaults can still override it, which is upstream's convention since `Kconfig.defaults` was introduced. Recorded in contract additions.
- **`zmk_backlight_update_vals` clamps** `brightness` to 100. The pin stored it raw. This is a one-line deviation at a trust boundary (the value comes off BLE) and changes nothing for in-range values.
- **`backlight.h` gains `<stdbool.h>`/`<stdint.h>`** because it now defines a struct that S3's `split/peripheral.c` includes.
- **Interim state:** after S1-T3 and before S3, `&bl` changes only the left half, because the right half gets no INVOKE_BEHAVIOR and no sync yet. Hardware is flashed only once C1–C9 have all landed (spec, Testing 3), so nobody runs this state.
- **Ext-power on the board:** `CONFIG_ZMK_RGB_UNDERGLOW_EXT_POWER=y` on both halves (S0-T2). Before T3, both UF2s link `settings_handler_ext_power`, `ext_power_settings_set`, `ext_power_settings_commit` and `ext_power_save_state_work`. After T3 none are linked, and ext power comes up on at every boot (the Kinesis behaviour). An `ext_power/state/*` key already in NVS from older firmware has no handler and is ignored.
- **R4 status.** The task brief marks R4 "RESEARCH FAILED", but `docs/research/R4.md` is complete and this plan builds on it: Zephyr drift is nil for these files, the files are byte-identical at the merge-base, and it gives the test-conf recipe. Nothing was assumed beyond it. Every claim above was re-verified in the prototype.

  ```c
  int zmk_backlight_update_vals(struct backlight_state new_state);
  ```
  Semantics S3 relies on: it sets `on`, sets `brightness = MIN(new_state.brightness, 100)`, applies it (local `BRT_SCALE` applied once) and schedules the debounced settings save. It returns 0 or the negative LED error. It is callable from the system work queue, where S3's peripheral handler runs (R1 §2). S3's central sender must send the **unscaled** `state.brightness`, not `zmk_backlight_get_brt()` scaled (Review Focus 1). `get_brt()` returns 0 while off, so to keep brightness across off/on S3 sends the raw state. The struct is readable only inside `backlight.c`, so S3 either adds `struct backlight_state zmk_backlight_get_state(void)` there as a K2 member or sends from inside `zmk_backlight_update()`, where `state` is in scope.

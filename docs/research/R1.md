# R1 — Custom central→peripheral command over upstream split transport

Feeds S3 (C3, contracts K1/K3/K4). Everything below was read from, or built against,
`zmkfirmware/zmk` `main` @ `9ebbeff0` in `/Users/adam/src/zmk-adv360`. Line numbers are on
`9ebbeff0` unless marked "prototype".

## TL;DR for S3

1. **Two BLE paths exist on main, and they are not the same shape.** `INVOKE_BEHAVIOR` reaches
   `peripheral.c`'s dispatcher (`zmk_split_transport_peripheral_command_handler`), but
   `SET_HID_INDICATORS` and `SET_PHYSICAL_LAYOUT` over BLE never do: `service.c` raises the
   event / calls the API directly from its own GATT write handler. Only the **wired**
   transport sends every command through the dispatcher. The prototype routes the new LED
   command through the dispatcher on both transports, so S3 applies it in one place.
2. **Main has no "peripheral (re)connected, re-send state" hook on the central.** HID indicators
   are *not* re-sent on reconnect (only the physical layout is, via its own work item). The
   central-side `zmk_split_peripheral_status_changed` event that the Kinesis pin relied on is
   raised only by the *peripheral* on main. The prototype adds the hook inside the split layer:
   `split/central.c` caches the last LED command and replays it from the transport status
   callback. The BLE transport fires that callback again once every handle is discovered and
   again once the link is encrypted. No feature code is involved and there is no 2.5 s timer.
3. **The shared BLE command queue can delay key-driven traffic (Review Focus 2).** Main's
   `zmk_split_central_split_run_msgq` (5 slots) carries `INVOKE_BEHAVIOR`, `SET_HID_INDICATORS`
   and `SET_PHYSICAL_LAYOUT`. When it is full, `k_msgq_put(..., K_MSEC(100))` **blocks the caller
   for up to 100 ms**, then pops the **oldest** entry, which may be an `INVOKE_BEHAVIOR`. Callers run
   on the system work queue, and that queue also drains the central's peripheral key-event
   queue (`peripheral_event_msgq`: 5 slots, `K_NO_WAIT` put with the error ignored). A stall there
   silently drops peripheral key events. So **LED sync must not go through the shared queue.** The
   prototype gives it its own `k_msgq` (`CONFIG_ZMK_SPLIT_CENTRAL_KINESIS_LED_QUEUE_SIZE`, K4),
   which enqueues `K_NO_WAIT` and drops the oldest *sync* entry when full. It is drained by a
   separate `k_work` on the same `split_central_split_run_q` thread, so no new thread or stack
   is needed and the Kinesis `*_STACK_SIZE` symbols stay dropped (K4).
4. **Put new GATT characteristics at the end of the service.** `service.c` notifies through
   hard-coded attribute indices `split_svc.attrs[1]` (position, line 221) and `attrs[8]` (sensor,
   line 267). The Kinesis pin inserted LED/BL right after run-behavior, which shifts `attrs[8]`
   whenever sensors are enabled. It also re-parents the `NUM_OF_DIGITALS` descriptor onto the
   BL characteristic. The prototype appends after the physical-layout characteristic.
5. The prototype **builds for both halves, in both variants**, is clang-format clean, and passes
   all 7 BabbleSim split tests, including a new `tests/ble/split/kinesis-led` that shows the replay
   reaching the real peripheral dispatcher (§5, re-run 2026-09-27). The full diff is in §7.
6. **Replay must not send state that was never set.** The prototype replays its zero-initialised
   cache, so a peripheral that connects before the first `zmk_split_central_update_kinesis_led`
   call receives `layer 0 effect 0 on 0`, i.e. "underglow off". The BSim run shows exactly this
   (§5). S3 adds a `has_state` flag to the cache, or S2 calls the helper once at central init.
   The prototype keeps the zero replay so the test has something to observe without a caller.
7. **R2 and R4 reconcile with this design** as shown in §2a. One conflict is resolved here: R4's table says
   "add `SET_KINESIS_*` cases to `split_central_split_run_callback`, no private queues". R1
   overrides that for RF2. The sync commands get their own msgq, drained by their own work item on
   upstream's existing `split_central_split_run_q` thread, so there is still no private thread and no
   `*_STACK_SIZE` symbol.

### How the central finds the new handle

The new characteristic is found by the same characteristic-discovery pass that finds every
other handle (§1b step 8): a new `else if (!bt_uuid_cmp(chrc->uuid, ZMK_SPLIT_BT_CHAR_UPDATE_LED_UUID))`
arm stores `bt_gatt_attr_value_handle(attr)` into `slot->update_led_handle`. The handle is added
to the `subscribed` conjunction, so discovery keeps walking until it is found. Both halves are
always flashed together (K3), so a peripheral without the characteristic is not a supported
state. If it did happen, discovery would run to the end of the service and LED sync would stay
disabled; keys would be unaffected.

### How commands are queued and sent

```
feature code (S2 tick / S1 listener, any thread)
  └─ zmk_split_central_update_kinesis_led(layer, effect, on)        split/central.c
       ├─ kinesis_led_cmd = {...}   (cache for replay)
       └─ for each connected source: bt send_command(source, cmd)
            └─ kinesis_sync_enqueue(): k_msgq_put(K_NO_WAIT); on full, get+drop oldest, retry
               k_work_submit_to_queue(&split_central_split_run_q, &kinesis_sync_work)
                 └─ kinesis_sync_work_cb (split_run_q thread)
                      skip unless slot CONNECTED && update_led_handle && security ≥ L2
                      bt_gatt_write_without_response(conn, handle, {layer,effect,on}, 3, true)
peripheral BT RX thread
  └─ split_svc_update_led(): validate offset/len → static copy → k_work_submit
       └─ system work queue: zmk_split_transport_peripheral_command_handler(bt, cmd)
            └─ peripheral.c case SET_KINESIS_LED   (S3: → zmk_rgb_underglow_set_periph)
```

The caller never blocks. A full queue costs one stale sync message, never a behavior or key event.
LED state is absolute (latest wins), so dropping the oldest is lossless in effect. A later
simplification would be a single "latest pending state + dirty flag" per source in place of a
queue. The prototype keeps the queue because K4 names a queue-size symbol.

## 3. Review Focus 1: how the central knows a peripheral (re)connected

**On main:** `split_central_connected` (922) and `split_central_disconnected` (951) submit
`notify_status_work`, which calls the registered `transport_status_cb` (`split/central.c:199`)
with the aggregate status (`DISCONNECTED` / `SOME_CONNECTED` / `ALL_CONNECTED`). The status
carries no per-source detail. `split/central.c` uses it only to re-select a transport when the
status is `DISCONNECTED`. Nothing re-sends HID indicators. The physical layout is re-sent by
its own mechanism: `update_peripherals_selected_layouts_work` is submitted when its handle is
discovered (616) and from `split_central_security_changed` (1003).

**Why "connected" is too early:** at `connected` time, no handles are discovered yet and the link
is not encrypted. Every split characteristic is `PERM_WRITE_ENCRYPT`, and the central never calls
`bt_conn_set_security` itself (`grep` finds only the two `bt_conn_get_security` checks). Encryption
comes later, triggered by the encrypted CCC subscribe. A write-without-response sent before that
point is silently dropped by the peripheral. The Kinesis pin worked around this with a fixed
`k_work_reschedule(&led_update_work, K_MSEC(2500))` in `rgb_underglow.c` after it raised
`zmk_split_peripheral_status_changed{.connected=true}` from the central's `connected` callback.
That callback runs on the BT RX thread.

**Prototype:** the BLE transport submits `notify_status_work` at the two moments a write can first
succeed:

- discovery complete (`subscribed` became true), and
- `security_changed` with `level >= BT_SECURITY_L2` and no error.

Either may come first, and both triggers are needed. Upstream's `split_central_security_changed`
returns early while `selected_physical_layout_handle` is 0, so if encryption completes before
discovery reaches that handle, the security trigger never fires. Discovery then completes on
an already-encrypted link, and the discovery trigger delivers the replay. `subscribed` requires
`selected_physical_layout_handle` (main `central.c:688`), so a discovery-complete trigger always
lets a later `security_changed` pass that guard. The BSim run (§5) shows the order security,
then LED handle, then replay. `split/central.c`'s status callback calls `resend_peripheral_state()`,
which re-broadcasts the cached LED command, for any non-`DISCONNECTED` status of the active
transport. Early replays are dropped by the readiness check in `kinesis_sync_work_cb`, and the
later trigger delivers the replay. Duplicates are harmless because the state is absolute. The
wired transport raises the same status callback on its detect-GPIO change, so the replay is
transport-agnostic. **Recommendation for S3:** add the current HID indicators
(`zmk_hid_indicators_get_current_profile()`) and backlight to `resend_peripheral_state()`. That
fixes the right half's caps-lock indicator staying stale after a reconnect, which main has today.

Test to own (S3): on hardware, power-cycle the right half and change the layer while it is off.
The right half's LOG_INF line (or, after S2, its colour) must show the new layer within one
connection interval of the `security_changed` log. No native_sim coverage is possible, because
BLE split is not simulated.

## 4. Review Focus 2: queues whose overflow could delay key events

| Queue (main) | Depth | Put | Full behavior | Risk to keys |
|---|---|---|---|---|
| central `peripheral_event_msgq` (`bluetooth/central.c:146`) | `CONFIG_ZMK_SPLIT_BLE_CENTRAL_POSITION_QUEUE_SIZE`=5 | `K_NO_WAIT` from the BT RX thread, **return ignored** | the **newest peripheral key event is silently lost** | Drained by `peripheral_event_work` on the **system work queue**. Anything that blocks that queue lets key events from the right half drop (stuck or missed keys) |
| central (left-half) `physical_layouts_kscan_msgq` (`physical_layouts.c:214`) | `CONFIG_ZMK_KSCAN_EVENT_QUEUE_SIZE`=4 | `K_NO_WAIT` from kscan callback, return ignored | newest local key event lost | Also drained on the **system work queue** (`msg_processor.work`). The left half's own keys have the same exposure to a stalled system work queue |
| central `zmk_split_central_split_run_msgq` (1022) | `..._SPLIT_RUN_QUEUE_SIZE`=5 | `K_MSEC(100)` | blocks the caller ≤100 ms, then drops the **oldest** (could be `INVOKE_BEHAVIOR`) | Callers are `zmk_split_central_invoke_behavior` (keymap, system work queue) and `hid_indicators.c` (system work queue). A burst of sync traffic on this queue would stall the system work queue → the row above |
| peripheral `position_state_msgq` (`service.c:214`) | `..._PERIPHERAL_POSITION_QUEUE_SIZE`=10 | `K_MSEC(100)` | blocks ≤100 ms, drops oldest bitmap | Holds full 16-byte state snapshots, so dropping the oldest loses no final state. Not touched by LED sync (opposite direction) |
| wired `tx_buf` / peripheral `cmd_msg_queue` (3) | `..._WIRED_CMD_BUFFER_ITEMS` / 3 | non-blocking | drops newest | n/a for adv360 (no wired DT) |
| Kinesis pin LED/BL msgqs | 5 each | `K_MSEC(100)` | blocks ≤100 ms, then drops oldest | Their drain `return`s (instead of `continue`) while the peripheral is disconnected, so the queue stays full. With the right half asleep, each further send blocks its caller for 100 ms. Most sends come from the underglow tick on the low-priority work queue, but `usb_conn_state_changed` and on/off handlers call it in event context |

**Answer:** yes. On main, the shared `split_run` queue is the one whose overflow can delay key
handling: its 100 ms blocking put runs on the system work queue, which also drains
peripheral key events, and that queue's put drops on overflow. The prototype keeps LED sync off
that queue entirely: separate msgq, `K_NO_WAIT`, drop-oldest-sync. Two shared resources remain:

- **The `split_central_split_run_q` thread.** A sync write can run ahead of an `INVOKE_BEHAVIOR`
  write. On Zephyr 4.1 that thread allocates ATT PDUs with `K_FOREVER` (R2 P3; only the system
  work queue and the ATT RX thread get `K_NO_WAIT`). So when the ATT TX pool is empty, the sync write
  **blocks until a buffer frees**, and that wait is longer than the call itself. Upstream's
  own commands have the same exposure.
- **The ATT TX buffer pool** (`BT_ATT_TX_COUNT`, set to 10 by `app/src/split/bluetooth/Kconfig:25`).
  It is shared with the HID reports to the host, which `hog.c` sends from its own `hog_work_q`
  and which also wait. At most `QUEUE_SIZE` (5) sync PDUs are outstanding per burst. That is
  bounded, but only if S2 **sends on change only**, as the Kinesis pin does (layer or effect
  changes), and never from a periodic tick. S2's review should check this.

Neither path drops a key event. The worst case is a delay of a few connection intervals during a
lighting burst. S3/S5's queue-full
test should assert that `zmk_split_central_update_kinesis_led` returns 0 without blocking when
called `QUEUE_SIZE + 10` times back to back with no peripheral ready. The BLE central does not
build for native_sim, so that test needs the enqueue helper split out behind a small test hook,
or it has to run on hardware with logging.

## 6a. Open questions for the critic

1. **K1 guard.** K1 guards the helper with `CONFIG_ZMK_RGB_UNDERGLOW`. The prototype uses the proposed
   `CONFIG_ZMK_SPLIT_KINESIS_LED` (`default ZMK_RGB_UNDERGLOW`, user-settable so BSim can enable it
   without a strip). If a user turned it off while leaving underglow on, S2's call would stop compiling.
   Options: record the symbol in K4 and have S2 guard on it, or keep K1's header guard and make
   the symbol `def_bool ZMK_RGB_UNDERGLOW || ZMK_SPLIT_KINESIS_LED_TEST`. R1 recommends recording it in K4.
2. **Queue vs coalesce.** K4 names queue-size symbols, so the prototype uses a queue. A per-source
   "latest state + dirty bit" needs no queue at all and cannot overflow. That would make
   `..._QUEUE_SIZE` unused, so it needs a K4 change first.

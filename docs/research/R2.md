# R2 — Do the Kinesis split BLE lockup fixes still apply on `main`?

Gates spec row C6 and section S5. Inputs: code repo `/Users/adam/src/zmk-adv360`,
Kinesis ref `kinesis/adv360-z3.5-2`, merge-base `3377ed02`, upstream `main` @ `9ebbeff0`.

## Verdict

None of the Kinesis `central.c` "lockup" commits fixes upstream code. Every guard they add
sits inside the Kinesis-only LED/backlight senders (`split_central_split_led_callback`,
`split_central_split_bl_callback`), and `main` has no such senders. The guards themselves
are a copy of the pattern upstream added in `33e3b02d` (2024-09-23) after a real
split lockup (#2461), so the bug class is fixed upstream for upstream's own commands.

**S5 ports nothing into `central.c` as a standalone fix.** The guards must be
re-created inside S3's new `SET_KINESIS_LED` / `SET_KINESIS_BACKLIGHT` command
handling (rules in [Rules for S3](#rules-for-s3-binding-on-the-new-led--bl-commands)). S5's job
becomes a review/test pass that those rules hold.

No commit is STILL-PRESENT in upstream code.

## Per-commit detail

### 62f5ad22 — handle-not-discovered guard

Diff (both LED and BL callbacks, `central.c` +10): before calling
`bt_gatt_write_without_response(peripherals[0].conn, peripherals[0].update_led_handle, …)`,
skip with `LOG_ERR("handle not discovered")` if the handle is 0.

Bug: Kinesis raises `split_peripheral_status_changed{connected=true}` from
`split_central_connected` (net diff, line ~984 on the pin). `rgb_underglow.c:741` and
`backlight.c:206` answer with `k_work_reschedule(&led_update_work, K_MSEC(2500))`. If GATT
characteristic discovery hasn't reached char 0x07/0x08 within 2.5 s, the write runs with
handle 0. Zephyr's `bt_gatt_write_without_response_cb` begins with `__ASSERT(handle, …)`
(same in 3.5 and 4.1, see probe P3). With asserts off the command goes on air to handle 0 and is
dropped. With asserts on it becomes a fatal error.

Equivalent on `main`: no LED/BL sender. Upstream's senders all guard the handle:
`update_peripheral_selected_layout` returns `-EAGAIN` on handle 0 (with the comment
that a peripheral can count as connected before discovery finishes; added in `33e3b02d`).
The run-queue `INVOKE_BEHAVIOR` case checks `run_behavior_handle`, and `SET_HID_INDICATORS`
checks `update_hid_indicators == 0`.

| Question | Answer |
|---|---|
| Bug exists on `main`? | No, the code path doesn't exist |
| Upstream analogue | `33e3b02d` guard in `update_peripheral_selected_layout` (already in pin base) |
| Action | N/A here; S3 includes `handle == 0 → skip` in the new cases |

### fa653463 — security guard + early return

Diff: in both callbacks `continue` becomes `return` for the not-connected and
handle-0 cases. It also adds `if (bt_conn_get_security(conn) < BT_SECURITY_L2) return;`.

Bug: the peripheral's LED/BL characteristics use `BT_GATT_PERM_WRITE_ENCRYPT` (pin
`service.c:289,295`). Before pairing/encryption finishes, a write with `sign=true` on an
unencrypted link takes Zephyr's signed-write path (`BT_ATT_OP_SIGNED_WRITE_CMD`).
ZMK doesn't enable `CONFIG_BT_SIGNING` (`git grep BT_SIGNING 9ebbeff0 -- app` finds nothing),
so `bt_smp_sign` is the stub that returns `-ENOTSUP` and ATT logs `Error signing data`
(P3). Upstream shipped exactly this bug in `03b5b38b` (physical layout sync,
2024-09-06). Issue zmkfirmware/zmk#2461 reports the resulting symptom: the left half stops
working as soon as the right half powers on, `<bt_att> Error signing data` appears in the log,
and it happens with matching firmware on both halves. Upstream reverted it in #2462 (`d52bb040`) and re-landed it as
`33e3b02d` with three changes (diff in P2):
1. `bt_conn_get_security(slot->conn) < BT_SECURITY_L2 → -EAGAIN`,
2. a `security_changed` conn callback that re-submits the sync work once security ≥ L2,
3. the write moved out of the GATT discovery callback into `k_work_submit` (no longer
   issued from BT RX context).

`fa653463` (authored two months later) copies item 1 into the Kinesis LED/BL senders. It
does **not** copy item 2. Kinesis relies on the 2.5 s timer instead, so an LED/BL update
dropped for low security is never retried until the next lighting change.

The `continue`→`return` part is a second, separate change. It stops draining the msgq and
leaves stale entries queued until the next `k_work_submit`. That is harmless on Kinesis's
private LED queue. On `main` the new commands share upstream's
`zmk_split_central_split_run_msgq` with `INVOKE_BEHAVIOR` (plan K1 routes C3 through
`send_command`), so a `return` there would strand queued behavior invocations behind a
skipped LED write. It must be per-command skip (`break`/`continue`).

| Question | Answer |
|---|---|
| Bug exists on `main`? | Not in upstream code: upstream's pre-encryption sender (physical layout) is guarded since `33e3b02d` |
| Upstream fix for the mechanism | `33e3b02d` (re-land of reverted `03b5b38b`, issue #2461, revert #2462) |
| Action | N/A here; S3 adds the security guard **and** a `security_changed` re-send; never `return` from the shared run loop |

### acd06e17 — rebase repair

The pin before this commit had the LED/BL `else if` branches dangling after the
`switch` (not valid C). This commit moves them into the characteristic if/else chain and
reformats `subscribed` to require `update_bl_handle && update_led_handle` as well. Kinesis
code only. N/A → S3.

Side note for S3: requiring both handles for `subscribed` means a peripheral built without
RGB *or* backlight never hits the early `BT_GATT_ITER_STOP`. Discovery just runs to the end
(`!attr → "Discover complete" → STOP`, same on `main`), so it is only slower, not broken. Both
Adv360 halves enable both, so it's fine. Gate each term on its Kconfig if S3 keeps the
early-stop.

## Latent upstream observation (not a Kinesis fix, not in scope to port)

`SET_HID_INDICATORS` in upstream's run callback checks the handle but not security
(`awk '/CMD_TYPE_SET_HID_INDICATORS:/,/break;/'` on main central.c contains 0 `security`
matches). The handle is discovered before encryption completes, so a host indicator change
inside that window takes the signed-write path. That write fails with `-ENOTSUP` and the
indicator state is lost until the next change: a missed caps-lock LED on the right half, not a
lockup. Upstream doesn't re-send indicators on peripheral connect either
(`zmk_split_central_update_hid_indicator` has one caller, `hid_indicators.c:36`). Since
C1/C2 consume indicators from this command, S3 may want the same re-send-on-security
hook to cover indicators. Record it as an optional upstreamable fix, not a C6 port.

## Rules for S3 (binding on the new LED / BL commands)

1. In `split_central_split_run_callback`, add `case ZMK_SPLIT_TRANSPORT_CENTRAL_CMD_TYPE_SET_KINESIS_LED`
   and `…_SET_KINESIS_BACKLIGHT`. Upstream's `default:` does `return`, which abandons the rest
   of the queue, so an unhandled new type would strand queued key-behavior commands.
2. Each case skips (`break`) when `update_led_handle == 0` / `update_bl_handle == 0` and when
   `bt_conn_get_security(conn) < BT_SECURITY_L2`, like `update_peripheral_selected_layout`.
   Never `return` out of the loop.
3. Re-send current LED + BL state from `split_central_security_changed`, which already exists and
   today returns early unless `selected_physical_layout_handle` is set. That covers reconnect
   (Review Focus 1) and replaces the Kinesis 2.5 s timer and the central-side
   `split_peripheral_status_changed` raise. Send from a `k_work`, never from the BT
   callback context (the third change in `33e3b02d`).
4. LED/BL state is last-writer-wins. Upstream's producer `split_bt_invoke_behavior_payload`
   waits `K_MSEC(100)`, then pops the **oldest** entry of the shared queue (default 5) and
   retries. A burst of lighting syncs can therefore evict a queued `INVOKE_BEHAVIOR` key event,
   which violates Review Focus 2. Either give lighting its own queue (the K4
   `ZMK_SPLIT_CENTRAL_KINESIS_{LED,BL}_QUEUE_SIZE` symbols) or coalesce: keep the latest
   state in a static and submit one work item that reads it at send time, the way
   physical layout does with `zmk_physical_layouts_get_selected()`. Coalescing needs no queue.
5. Peripheral side: each new case in `zmk_split_transport_peripheral_command_handler` returns
   (#3120 lesson).

`split_central_split_run_q`.
